## 1. 项目一句话定位

在现有两台服务器（10.167.2.175 / 10.167.2.176）的 Kubernetes 集群及其已运行基础设施（TiDB、Pulsar、Milvus、NebulaGraph、Redis、LiteLLM/Ollama、Prometheus/Grafana/Loki 等）之上，按照 **"1+1+N"** 总体架构（1 个数字底座 + 1 个指挥中枢 + N 个场景应用），采用 **DDD + GraphQL Federation + 读写分离 + 多级缓存 + 事件驱动 + AI 智能体（MCP/A2A）** 的现代工程体系，建设支撑 **100 万用户** 的数字乡村综合应用系统。

## 4. 关键技术决策（一页纸）

| 决策点 | 选型 | 理由 |
|---|---|---|
| API 风格 | GraphQL Federation 2（Apollo Router + DGS 子图） | 前端一端多态聚合、按需取数、企业级高性能路由（Rust），集群内 qianrenqianmian 已有 graphql-gateway 先例 |
| 后端语言 | Java 21（虚拟线程）+ Spring Boot 3.x，六边形架构；AI 服务 Python FastAPI | 与集群既有 Java 服务栈一致；虚拟线程支撑高并发 IO |
| 主数据库 | TiDB（已有，2 TiDB + 3 TiKV + 3 PD + TiFlash） | HTAP、水平扩展、读写分离（写主/读副本池 + TiFlash 分析副本） |
| 缓存 | L1 Caffeine(进程内) → L2 Redis Cluster → Nginx micro_cache → CDN（外购建议） | 四级缓存命中率目标 ≥90%，保护 TiDB |
| 消息/事件 | Pulsar（已有，2 broker + 2 bookie） | 领域事件、IoT 遥测、削峰、Outbox 模式 |
| 向量检索 | Milvus（已有） | RAG 检索 |
| 知识图谱 | NebulaGraph（已有） | 人-地-物-组织-事件关系图谱 |
| LLM | LiteLLM 统一网关（已有）→ Ollama 本地模型 + 外部大模型双轨 | 数据不出域可切本地；成本敏感可切外部 |
| 智能体协议 | **MCP（工具接入）先行 + A2A（智能体协作）预留** | 2026 企业最佳实践：MCP 管工具、A2A 管协作；集群内 mcp-fnb-tools 已有先例 |
| 观测 | OpenTelemetry → Prometheus + Loki + Grafana（已有）+ Jaeger（新增，可选） | 统一指标/日志/追踪 |
| CI/CD | Git + 集群内 Registry(10.167.2.175:30500) + Kustomize/Helm + ArgoCD（可选） | 复用私有镜像仓库，GitOps 渐进 |
| 压测 | k6（集群内有 k6-loadgen 先例） | 阶梯压测至 100 万用户模型 |
| 前端 | Vue3 + Vite + Element Plus；小程序 uni-app；大屏 ECharts | 主流、人才好找 |

## 5. 100 万用户容量结论（详见 08 号文档）

- **术语澄清**：100 万注册用户 ≠ 100 万并发连接。按行业模型：峰值同时在线 10%（10 万），峰值网关 QPS ≈ 1 万（常规）～3 万（突发）。
- **当前 2 节点集群**（可分配约 45 核 / 95GB）：在多级缓存命中率 ≥90% 的架构下，可支撑 **5～10 万同时在线**，满足试点县（县域常住 30-60 万人）一期目标。
- **100 万用户路径**：架构全无状态 + HPA 水平扩展，扩容至 8-12 台应用节点 + CDN 卸载静态与热点流量后达成；扩容不停服、不改代码。
- 该结论为诚实的工程测算，写入 08 号文档容量数学模型，任何"两台机器扛百万人"的说法都是不科学的——本方案以架构就绪 + 分期扩容兑现指标。
