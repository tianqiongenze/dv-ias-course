# 08 高并发容量设计与性能保障（100 万用户）

> 方法论：需求量化 → 负载模型 → 资源数学 → 架构手段 → 验证闭环。**先给结论，后给推导。**

---

## 1. 结论（诚实工程声明）

| 阶段 | 用户规模 | 同时在线 | 网关QPS | 支撑条件 | 硬件 |
|---|---|---|---|---|---|
| 一期（试点县） | 30-60 万注册 | 5-10 万 | 5K-1万 | 缓存命中≥90% | **现有 2 节点**（预算 40C/80G） |
| 二期（扩容） | 100 万注册 | 20-30 万 | 2-3 万 | +CDN 卸载 60% | +4 应用节点 |
| 三期（满配） | 300 万+ | 100 万在线 | 8-10 万 | 全链路多级缓存+单元化 | +8-12 应用节点 |

> 说明："100 万人同时使用"在行业口径中通常指**系统注册容量 100 万、峰值并发在线 10%**。本架构按无状态水平扩展设计，扩容只需加节点+接 CDN，不改代码；两台机器物理上无法承载 100 万真实并发长连接（仅 TCP 内存就不止 250G），这是数学而非态度——扩容路径已给足。

## 2. 负载模型推导

### 2.1 流量画像（数字乡村业务特点：读>>写，潮汐明显）

| 业务 | 读:写 | 高峰 | 峰值占比 |
|---|---|---|---|
| 村务公开/资讯浏览 | 100:1 | 早 7-9、晚 19-22 | 40% |
| 事件上报/处置 | 10:1 | 工作时段 | 15% |
| AI 问答 | 1:1(对话) | 晚间 | 15% |
| 积分/商城 | 8:1 | 晚间/活动 | 10% |
| IoT 遥测（后台） | 写为主 | 持续 5K 点/s | — |
| 大屏/报表 | 聚合读 | 工作时段 | 5% |

### 2.2 QPS 推导（100 万注册用户）

```
DAU 40% = 40万活跃；峰值小时集中系数 0.3 → 峰值 12万 在线
人均操作 1次/15s（浏览型）→ 峰值请求 12万/15 ≈ 8,000 rps
突发场景（投票开启/公告推送）×3 → 24,000 rps 设计目标（二期）
其中静态+可缓存公开内容 ≈ 70% → 命中 CDN/Nginx/Router 缓存后回源 ≤ 7,200 rps
回源中可被 Redis 命中 ≥70% → TiDB 读池实际 ≤ 2,200 rps，写 ≤ 800 rps
```

## 3. 资源数学（当前集群预算 40C/80G）

|---|---|---|---|
| apollo-router | ~4K rps（简单查询，2C） | 2×(1C/512M)→HPA4 | 网关 1.6 万 rps |
| Java 领域服务（虚拟线程） | ~1.5K rps 读（2C，缓存命中） | 12 服务×2×(1C/1.5G) | 分域承载 |
| realtime-gateway | 2 万 WS 连接（2C） | 2×(1C/1G) | 4 万长连接 |
| agent-runtime | 20 并发会话（1C/2G，本地模型） | 2 | 40 并发 AI；外部模型无此限 |
| iot-ingest | 5K msg/s（1C） | 2 | 1 万点/s |
| Redis 集群 | 8 万 OPS/节点 | 3×(1C/6G) | 24 万 OPS |
| TiDB 读池 | 3K QPS（点查为主） | 已有 | 读写分离吸收 |
| 合计 requests | — | ≈ 38C / 74G | 预算内 ✔ |

**一期验证目标**：k6 压到 1 万 rps（混合场景 8:1:1），P95≤200ms、错误率<0.1%、TiDB CPU<60%。

## 4. 架构手段清单（逐层削峰）

1. **静态与媒体**：720°全景、图片走 CDN（对象存储回源）；未购 CDN 前用 Nginx `proxy_cache`+ `Cache-Control: immutable`。
2. **公开读**：Nginx micro_cache 10s + Router 响应缓存 30s —— 公告类峰值天然被吸收。
3. **列表/详情**：Caffeine L1 + Redis L2（05 号文档失效矩阵）；防击穿三件套。
4. **写削峰**：投票/上报先入 Pulsar（客户端乐观返回"已提交"），消费者落库；控制指令双签后异步执行。
5. **热点账户**（积分、库存）：Redis 原子扣减 + 异步落库 + 对账，避免行锁热点；榜单独立计数器。
6. **遥测**：批量聚合写（500 条/批或 1s flush）。
7. **大屏**：指标服务推送快照（WS），N 客户端共享一份计算。
8. **限流熔断**：网关层（用户/IP/API 三维令牌桶）→ 服务层（Sentinel 规则：QPS/并发/热点参数）→ 依赖层（舱壁隔离，AI/支付/政务各自线程池）。
9. **HPA**：CPU 60% 扩容 2→8；realtime 按自定义连接数指标；K8s PDB 保证滚动更新容量不减。
10. **优雅降级**：AI→FAQ 模板；支付→线下；政务→申报制；大屏→静态快照（P8 原则）。

## 5. 数据库瓶颈推演

| 风险 | 触发 | 预案 |
|---|---|---|
| 单表过大（积分流水 2 亿） | 三年 | 按月分区+归档；查询走 ledger 索引+分页游标 |
| 热点行（某村公告 counters） | 推送峰值 | Redis 计数+异步聚合，DB 只存分钟级快照 |
| TiKV 写入 | >5K rps 写 | 批量合批；再扩 tikv（运维动作，不停服） |
| TiFlash 查询并发 | 大屏并发聚合 | dws 物化表承接，TiFlash 仅批算 |

## 6. 性能预算（端到端，一期验收线）

```
小程序首屏 ≤2.0s（CDN 命中）
公开页查询  P95 ≤120ms（Nginx 缓存命中）/ ≤200ms（回源 Redis 命中）/ ≤500ms（穿透DB）
事件上报    P95 ≤400ms（含 Pulsar 异步解耦）
AI 问答     首 token ≤2s；完整 ≤8s
大屏快照    ≤1s
WS 推送     端到端 ≤1.5s
```

## 7. 验证闭环

- 基准：每服务 `k6 smoke`（CI 内）→ 环境 `k6 load`（夜跑）→ 版本 `k6 stress`（找拐点）→ 演练 `k6 soak`（8h 稳定性+内存泄漏）。
- 混沌演练（staging）：杀 Pod、断 Pulsar、Redis 超时、TiDB 读池不可用——验证降级路径（P8）。
- 容量看板：Grafana 容量视图（QPS/延迟/命中率/队列积压/TiDB CPU），月度容量评审，触发 70% 水位即启动扩容流程。
