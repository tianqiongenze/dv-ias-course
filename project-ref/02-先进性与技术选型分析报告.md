## 2. 技术选型决策矩阵

对每项候选按 **成熟度/团队技能/集群匹配度/社区活跃度/许可** 五维打分（5 分制），仅列关键项。

### 2.1 API 层：GraphQL Federation 2

| 候选 | 成熟 | 技能 | 集群匹配 | 活跃 | 许可 | 结论 |
|---|---|---|---|---|---|---|
| **Apollo Router（Rust）** | 5 | 4（运维简单） | 5（单二进制容器） | 5 | Apache-2（企业版功能受限但够用） | **选用** |
| Hive Router（The Guild, 2025 新） | 4 | 4 | 5 | 4 | MIT | 备选（性能同级，生态更新） |
| Node.js Apollo Gateway | 4 | 5 | 4 | 4 | MIT | 不选（性能上限低） |
| 自研 Node BFF（qianrenqianmian 模式） | 3 | 5 | 5 | 3 | — | 不选（无联邦能力） |

依据：2026 年联邦网关最佳实践共识——Rust 系路由（Apollo Router / Hive / Cosmo）为高并发标配，配 APQ 缓存预热、查询计划优化、限制子图扇出。（调研来源见文末）

**子图框架**：Netflix DGS（Java，与 Spring Boot 3 无缝）。理由：DGS 是 Java 生态联邦子图事实标准，支持联邦 2 指令、代码生成、易于 TDD。

### 2.2 后端运行时

- **Java 21 LTS + Spring Boot 3.x + 虚拟线程（JEP 444）**：IO 密集型服务单 Pod 承载能力较平台线程提升 5-10 倍，免响应式编程复杂度；与集群既有 Java 服务栈（qianrenqianmian undertow 系列）技能延续。
- **Python 3.12 + FastAPI**（仅 AI 服务）：生态（LangChain/LangGraph、ultralytics）不可替代；集群 fnb-prod agent-runtime 已验证该模式。
- 架构风格：**六边形（端口与适配器）+ DDD 战术模式**，依赖单向：adapter → application → domain。

### 2.3 数据层

| 用途 | 选型 | 先进性论据 |
|---|---|---|
| OLTP 主库 | TiDB（已有 2×tidb） | HTAP 存算分离，兼容 MySQL 生态；读写分离以"连接池标签 + 独立读服务"实现（集群已有 `tidb-read` ExternalName 先例） |
| 分析查询 | TiFlash（已有） | 列存副本，副本一致性读 `isolation_read_engines=tiflash`，大屏/报表不扰 OLTP |
| 缓存 L2 | Redis 7 Cluster 3 主（新建于 infra） | 集群已有 redis8 三节点运行经验；主从+槽分片支撑 10 万级 OPS |
| 缓存 L1 | Caffeine（Java 进程内） | JVM 事实标准，W-TinyLFU 命中率高 |
| 消息 | Pulsar（已有） | 存算分离、分层存储、百万 topic；领域事件 + IoT 遥测 + Outbox |
| 向量 | Milvus（已有） | RAG 标配；HNSW/IVF 索引 |
| 图谱 | NebulaGraph（已有） | 国产开源图库，人-地-物-组织-事件关系网络（治理一张图的关系侧） |
| 对象存储 | MinIO（milvus-minio 已有）+ NFS | 图片/全景素材/附件 |
| 时序（IoT） | 方案 A：TiKV 直写 + 按天分区表；方案 B：新增 TDengine | **选 A**：不新增组件，遥测 5K 点/s 规模 TiDB 足够（验证于 08 号文档容量测算） |

### 2.4 AI 与智能体（2026 前沿重点）

**分层架构（业界 2026 共识模式：MCP 先行、A2A 预留）**

```
用户 ─▶ 智能体运行时(LangGraph编排) ─┬─▶ MCP Client ─▶ mcp-dv-tools(MCP Server: 业务查询/办理)
                                   ├─▶ RAG: Milvus检索 + vector-reranker重排
                                   ├─▶ LLM: LiteLLM网关 ─▶ Ollama本地 / 外部大模型
                                   └─▶ A2A(预留): 与县级政务智能体互操作(Agent Card发现)
```

| 决策 | 论据（含调研结论） |
|---|---|
| MCP（Model Context Protocol）作为工具接入层 | 2026 企业智能体事实标准：智能体↔工具/数据统一协议；集群已有 mcp-fnb-tools 运行先例，模式可复制 |
| A2A 作为智能体间协作预留 | Google 主推、Linux 基金会托管；2026 最佳实践"先 MCP 后 A2A"——本项目实现 Agent Card 发布 + 任务委托接口，但不强依赖 |
| LangGraph 做编排 | 有状态多轮、检查点、人机协同（HITL）节点——办事审核类流程必需 |
| RAG：混合检索（BM25+向量）+ 重排 | 集群已有 Milvus + vector-reranker；中文分词 IK；引用溯源防幻觉 |
| 本地模型兜底 | Ollama（qwen2.5-7b/14b 级别）保证"数据不出域"模式可用；LiteLLM 双路由（本地优先/外部优先可配） |
| CPU 推理（无 GPU 约束下） | 图像：YOLOv8n int8 量化 + PP-LCNet，单核 5-15 FPS，分时批处理满足"截图巡检"非实时场景；文本：qwen 小尺寸 + vLLM CPU 版后续可评估 |

### 2.5 前端与端侧

- Vue 3.4+ + Vite 5 + TypeScript + Element Plus（管理端）、uni-app（H5/小程序同构）、ECharts + 高德 JS API（大屏/GIS）。
- 微前端：一期不需要（单一团队）；预留 Module Federation 演进路径。
- UI 设计语言：以"绿水青山"乡土色系（主色 #2E7D32 松绿、辅色 #F9A825 谷黄）+ 大字号适老化（村民端字号 ≥16px，支持长辈模式）——由资深美工视角落实到设计系统（design tokens 见 06 号文档附录）。

## 3. 与"先进性"相对的克制（架构师判断）

明确**不采用**的技术及理由（防止过度设计，同样是先进性的一部分）：

1. **Service Mesh（Istio）**：集群 istio-system 为空，2 节点规模下 sidecar 开销 > 收益；用 SDK + 网关层治理。
2. **Kafka 替换 Pulsar**：Pulsar 已在运行，功能覆盖需求，重复建设违背指南 2.0。
3. **真区块链**：溯源场景用国密哈希锚定 + 可信时间戳即可满足存证与核验，链的成本与运维复杂度不成比例（如后续监管要求可平滑升级为联盟链）。
4. **Knative/Serverless**：流量模型常驻为主，K8s Deployment+HPA 足够。
5. **多语言后端**：仅 Java + Python 两种，控制认知与运维成本。
